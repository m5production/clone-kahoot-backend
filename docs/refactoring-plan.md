# План рефакторинга бэкенда

Дата: 2026-11-18.

Этот документ фиксирует план, а не текущее устройство приложения. Прогресс реализации отмечается в [чеклисте](./refactoring-checklist.md). Полную документацию архитектуры и модулей заполняем после выполнения плана по фактически реализованному коду.

## Цель и принятые решения

Перевести бэкенд на модульный монолит на NestJS, исправить проблемы безопасности и целостности данных, покрыть ключевые сценарии тестами и описать архитектуру в `backend/docs/`.

Целевой стек:

- Node.js — production runtime.
- NestJS с Express-адаптером — HTTP.
- `ws` через NestJS-адаптер — WebSocket, без перехода на Socket.IO.
- PostgreSQL + Prisma — хранение данных.
- Biome вместо ESLint и Prettier — линтинг и форматирование.
- TypeScript — проверка типов.
- OpenAPI — документация HTTP API.

Существующие данные можно не переносить: для PostgreSQL создаётся новая начальная схема. Это не является разрешением немедленно удалить существующую базу: конкретный сброс или удаление необходимо подтвердить отдельно.

Переход с Yarn на Bun как менеджер пакетов не согласован и не является обязательной частью миграции. Production runtime остаётся Node.js.

Фронтенд адаптируется там, где обоснованно меняются авторизация или контракты. Изменения в backend и frontend проверяются и оформляются отдельно: это разные git-репозитории.

## 1. Целевая архитектура

```text
backend/
├── src/
│   ├── main.ts
│   ├── app.module.ts
│   ├── config/
│   ├── database/
│   │   ├── prisma.module.ts
│   │   └── prisma.service.ts
│   ├── common/
│   │   ├── filters/
│   │   ├── guards/
│   │   └── decorators/
│   └── modules/
│       ├── auth/
│       ├── users/
│       ├── games/
│       ├── questions/
│       ├── accepted-answers/
│       ├── active-game/
│       └── health/
├── prisma/
│   ├── schema.prisma
│   ├── migrations/
│   └── seed.ts
├── test/
└── docs/
```

Внутри модуля создавать только необходимые элементы: module, controller или gateway, service, DTO, policies и тесты.

| Элемент | Ответственность |
| --- | --- |
| Controller | HTTP-параметры, вызов сценария, ответ |
| Gateway | WebSocket-соединения, приём сообщений и отправка событий |
| DTO и validation | Проверка входных данных |
| Guard | Аутентификация и допуск к обработчику |
| Policy | Правила доступа к конкретному ресурсу |
| Service | Бизнес-сценарии и транзакции |
| Prisma | Запросы, связи и ограничения БД |
| Response DTO или mapper | Явный состав публичного ответа |

Модули взаимодействуют через экспортированные сервисы, а не чужие контроллеры или внутреннее изменяемое состояние. `common` содержит только действительно общие технические элементы, а не бизнес-логику.

Не добавлять заранее универсальный repository, базовые CRUD-сервисы, CQRS, event bus, микросервисы или отдельный query-класс для каждого простого запроса.

## 2. Фиксация контрактов

До переноса обработчиков:

1. Составить перечень HTTP-маршрутов и WebSocket-событий.
2. Проверить их использование фронтендом.
3. Разделить поведение на сохраняемые контракты, ошибки реализации и намеренные изменения безопасности.
4. Добавить проверки ключевых существующих сценариев.
5. Зафиксировать таблицу изменений контрактов.

По возможности сохранить пути `/api/...`, успешные ответы и имена событий. Не сохранять ради совместимости выдачу паролей, аутентификацию через произвольный ID, отсутствие проверки владельца, неверные коды ошибок и возможность управлять чужой игрой.

Опечатки протокола, включая `qusetionId`, исправлять согласованно с фронтендом либо через временный совместимый адаптер.

**Критерий готовности:** известны все необходимые изменения фронтенда; основные пользовательские сценарии защищены тестами. Тесты старого поведения не должны закреплять уязвимости как желаемое поведение.

### Инвентаризация исходных контрактов

| HTTP | Исходный контракт | Решение и frontend-правки |
| --- | --- | --- |
| POST `/api/users` | `{name,password}` → 201 `{id,name}`, ID в cookie | Сохранить регистрацию; выдавать токен серверной сессии, сохранять в localStorage |
| POST `/api/users/auth` | `{name,password}` → `{id,name}`, ID в cookie | Сохранить вход; выдавать токен; неверные credentials → 401 |
| GET `/api/users/:id` | `{id,name}`, устанавливает cookie | Только публичный профиль без создания сессии; frontend восстанавливает вход через текущую сессию |
| GET `/api/users/auth/:id` | `{isAdminUser}` из сравнения с ADMIN_ID | Не использовать как авторизацию; допуск ведущего определяется владением игрой |
| PUT, DELETE `/api/users/:id` | Обновляет/удаляет пользователя, возвращает полную модель | Только собственный аккаунт; исключить пароль/хеш из ответа |
| GET, POST `/api/games` | Список своих игр / создание → `{id,adminId}` | Сохранить форму; владельца определять по Bearer-сессии |
| GET, DELETE `/api/games/:id` | Игра / удалённая игра | Проверять владельца, каскадное удаление связанных данных |
| GET `/api/questions?gameId=…` | Массив вопросов | Для редактора только владельцу; явный порядок; игрок получает текущий вопрос через WS |
| GET, PUT, DELETE `/api/questions/:id` | Вопрос `{id,gameId,img,text}` | Проверять владельца; запретить перенос в чужую игру |
| POST `/api/questions` | `{gameId,img?,text}` → 201 вопрос | Проверять владельца и DTO |
| GET `/api/accepted-answers?questionId=…` | Массив `{id,questionId,text}` | Только владельцу, без раскрытия правильных ответов игрокам |
| POST `/api/accepted-answers` | Массив `{questionId,text}` → 201 `{count}` | Валидировать весь список и права перед записью |
| PUT `/api/accepted-answers?questionId=…` | Массив ответов → созданные ответы | Атомарная замена; запретить отличающийся questionId и лишние поля; frontend не отправляет id |
| DELETE `/api/accepted-answers?questionId=…` | `{count}` | Сохранить ответ; исправить frontend-тип, сейчас указан массив |
| GET `/api/active-game/:id` | `Game exists`, 404 нет игры, 403 другая игра | Перейти к адресации независимых комнат; отсутствие → 404 |

Исходный WS использует `{type,payload}` на корневом пути сервера:

| Событие клиента | Исходный payload | Решение |
| --- | --- | --- |
| START_GAME | `{gameId}` | Только владелец; вернуть идентификатор комнаты; изоляция комнат |
| PLAYER_CONNECTED | `{userId}` | Идентичность из сессии, не из payload; добавить адресацию комнаты |
| CHANGE_QUESTION | `{qusetionId}` | Исправить на questionId одновременно с frontend; только ведущий |
| ANSWER_QUESTION | `{playerId,questionId,answer}` | Игрок из сессии; только текущий вопрос своей комнаты; правило повторного ответа покрыть тестом |
| SHOW_ANSWERS | `{questionId}` | Только ведущий, раскрывать результаты явно |
| SHOW_WINNERS | `null` | Только ведущий своей комнаты |
| END_GAME | `null` | Только ведущий своей комнаты |

Исходящие события: GAME_DATA (состояние игры), FAULT (строка), SHOW_ANSWERS (массив ответов игроков с оценками), SHOW_WINNERS и END_GAME (null). Сохранить имена, разделить публичное состояние ведущего/игрока, заменить строковую ошибку структурированной. Не рассылать clientId и преждевременные оценки ответов.

Проверено использование во frontend: `src/entities/{user,game,question,accepted-answer}/*.api.ts`, `src/entities/active-game/`, `src/features/active-game/`. Требуются изменения восстановления входа/выхода, HTTP-interceptor с Bearer, типов ошибок, WS-билетов, выбора комнаты, payload команд и обработчиков завершения. Существующие frontend unit/component/e2e-проверки адаптировать вместе с контрактами.

## 3. Каркас NestJS и инструменты

1. Настроить NestJS с Express и префиксом `/api`.
2. Разделить создание приложения и запуск процесса для интеграционных тестов.
3. Добавить проверяемую конфигурацию: `NODE_ENV`, `HOST`, `PORT`, `DB_*` (DSN собирается из полей), разрешённые origin, сроки сессий и WS-билетов и proxy.
4. Настроить глобальную валидацию DTO с отклонением неподдерживаемых полей.
5. Заменить ESLint и Prettier на Biome.
6. Настроить команды разработки, сборки, production-запуска, lint/format check, typecheck и тестов.
7. Использовать поддерживаемые стабильные версии зависимостей и фиксировать lockfile.

**Критерий готовности:** приложение запускается, собирается, валидирует конфигурацию и проходит базовые проверки.

## 4. PostgreSQL и модель данных

Создать новую начальную Prisma-миграцию для PostgreSQL, не применять SQLite-миграции к новой СУБД.

Основные связи:

```text
User ──< Game ──< Question ──< AcceptedAnswer
  │
  └──< Session
```

Предусмотреть:

- Внешние ключи и индексы для связей и частых запросов.
- Уникальность имени пользователя.
- Хеш пароля вместо открытого пароля.
- Временные метки там, где нужны.
- Явный порядок вопросов вместо зависимости от порядка `findMany`.
- Обоснованные правила удаления связанных записей.
- Таблицу сессий.
- Ограничения длины и правила пустых значений для вопросов и ответов.
- Ограничения БД в дополнение к проверкам приложения, где применимо.

Окружение:

- Локальный PostgreSQL через Docker Compose.
- Отдельная тестовая БД.
- Шаблон переменных окружения без секретов.
- Seed для воспроизводимых локальных сценариев без production-паролей.
- Отдельная команда production-миграций при развёртывании, не запуск миграций каждым экземпляром приложения при старте.

**Критерий готовности:** новая БД разворачивается миграциями; seed, связи, ограничения и транзакции проверены интеграционными тестами.

## 5. Аутентификация и авторизация

Согласованный механизм для браузерной SPA — серверные сессии без JWT. При текущем cross-site размещении SPA и API случайный непрозрачный токен хранится в localStorage и передаётся через Authorization: Bearer. Риск кражи токена при XSS принят; токен нельзя включать в логи и URL. В БД хранится только хеш токена. Для WebSocket использовать одноразовый короткоживущий билет, получаемый авторизованным HTTP-запросом.

Аутентификация:

- Регистрация с подходящим алгоритмом хеширования паролей.
- Вход по имени и паролю.
- Случайный непрозрачный токен сессии в localStorage клиента, передаваемый через Authorization: Bearer.
- Хеш токена, срок действия и владелец в БД.
- Получение текущего пользователя.
- Выход с отзывом сессии.
- HTTPS в production; очистка токена на клиенте при выходе и истечении сессии. Cookie для аутентификации не используются.
- Исключение паролей, хешей и токенов из ответов и логов.

Авторизация:

- Изменение и удаление игры только владельцем.
- Права на вопросы и допустимые ответы через владельца игры.
- Управление игровой сессией только её ведущим.
- Ответ игрока только от собственного имени.
- Получение пользователя по ID не создаёт авторизованную сессию.

При размещении GitHub Pages и API на разных сайтах использовать Bearer-сессии, не полагаясь на third-party cookie. Проверять разрешённые origin и Origin при WebSocket-подключении; билеты должны иметь короткий срок действия и погашаться однократно. Изменяющие запросы требуют явного Authorization, а не автоматически отправляемой cookie. CORS не заменяет авторизацию.

**Согласовано:** ведущий и участники входят только через аккаунты; гостевой вход не реализуется.

**Критерий готовности:** проверены вход, выход, истечение сессии и отказ в доступе к чужим ресурсам.

## 6. CRUD-модули

Перенести `users`, `games`, `questions`, `accepted-answers`.

- Не передавать `req.body` напрямую в Prisma.
- Разделить DTO создания, обновления и ответа.
- Не возвращать Prisma-модель пользователя целиком.
- Устранить дублирующиеся проверки.
- Единообразно обрабатывать ожидаемые ошибки, конфликты уникальности и отсутствие записей.

Замена допустимых ответов:

1. Проверить вопрос и права.
2. Проверить весь входной список.
3. В одной транзакции удалить прежние ответы и создать новые.
4. При ошибке сохранить прежнее состояние.

Не позволять элементам списка подменять `questionId` и затрагивать другой вопрос.

**Критерий готовности:** проверены CRUD, отрицательные сценарии доступа и откат транзакции.

## 7. Проведение игры и WebSocket

Разделить gateway, бизнес-сервис и хранилище состояния. Убрать глобальную переменную из контроллера. Типизировать и валидировать входящие сообщения; определить отдельные публичные представления данных для ведущего и игроков.

Обязательные изменения:

- Обработка некорректного JSON, неизвестных событий и неверного payload.
- Проверка роли отправителя.
- Защита запуска игры от конкурентных команд.
- Привязка ответа к игроку и текущему вопросу.
- Явные правила повторного ответа.
- Рассылка только участникам нужной игровой сессии.
- Отсутствие утечки правильных ответов до разрешённого момента.
- Проверка состояния сокета перед отправкой.
- Heartbeat и очистка отключившихся соединений.
- Предсказуемая обработка отключения ведущего и игрока.

Согласованные требования:

- Несколько независимых одновременных игровых комнат.
- Активное состояние и результаты хранятся в памяти одного экземпляра сервера и теряются при перезапуске.
- Отключение ведущего завершает его комнату.
- Игрок с тем же аккаунтом может переподключиться в активную комнату с сохранением своих ответов.
- Постоянная история результатов в первой версии не реализуется.

Не добавлять Redis и распределённую координацию без подтверждённой необходимости. При хранении состояния в памяти явно документировать ограничение одного экземпляра игрового сервера и потерю активного состояния при перезапуске. PostgreSQL сам по себе не синхронизирует состояние процессов.

**Критерий готовности:** проверены полный игровой цикл, неверные команды, конкурентный запуск и отключения.

## 8. Ошибки, безопасность и эксплуатация

Единый формат HTTP-ошибок: `code`, `message`, `requestId`.

| HTTP-статус | Назначение |
| --- | --- |
| 400 | Некорректный ввод |
| 401 | Нет действующей аутентификации |
| 403 | Недостаточно прав |
| 404 | Ресурс не найден |
| 409 | Конфликт состояния |
| 500 | Неожиданная ошибка без раскрытия внутренних деталей |

Для WebSocket предусмотреть структурированные ошибки без разрыва соединения при обычной бизнес-ошибке.

Эксплуатационные меры:

- Структурированные логи и request ID без секретов.
- Защитные HTTP-заголовки.
- Лимиты HTTP body и WebSocket payload.
- Ограничение частоты входа и игровых команд.
- Корректная настройка reverse proxy.
- Liveness и readiness.
- Завершение HTTP, WebSocket и Prisma при `SIGTERM`/`SIGINT` с ограничением времени ожидания.

Docker и Amvera:

- Обновить Docker-сборку и команды запуска.
- Не встраивать production-секреты в образ.
- Запускать приложение непривилегированным пользователем.
- Проверить доступность PostgreSQL, хранение секретов и health checks на Amvera.
- Описать резервное копирование и проверку восстановления БД.

**Критерий готовности:** проверены запуск контейнера, health checks, ошибки и корректное завершение; инфраструктурные требования подтверждены для выбранного размещения.

## 9. Тестирование и CI

| Уровень | Проверки |
| --- | --- |
| Unit | Политики, игровые переходы и бизнес-правила |
| Integration | Prisma с реальным тестовым PostgreSQL, ограничения и транзакции |
| API / WebSocket | Контракты, Bearer-сессии, WS-билеты, авторизация и полный цикл игры |

Не заменять PostgreSQL на SQLite в интеграционных тестах.

CI:

1. Воспроизводимая установка зависимостей.
2. Генерация Prisma Client.
3. Biome check.
4. Typecheck.
5. Unit-тесты.
6. Миграции тестового PostgreSQL.
7. Integration и API/WS-тесты.
8. Production-сборка.

Содержание:

- `architecture.md`: структура, зависимости, границы и причины решений.

Каждый модуль описать по единому шаблону:

1. Назначение.
2. Данные и правила, которыми он владеет.
3. Публичные HTTP/WS-интерфейсы.
4. Зависимости.

## Порядок реализации

1. Инвентаризация контрактов и тесты основных сценариев.
2. Каркас NestJS, конфигурация, Biome и тестовая инфраструктура.
3. PostgreSQL, схема и миграции.
4. Аутентификация и политики.
5. CRUD-модули.
6. WebSocket и игровая логика.
7. Согласованные изменения фронтенда.
8. Docker, CI и эксплуатационные проверки.
9. Полное заполнение документации и финальная проверка пользовательского сценария.

Тесты добавлять при реализации каждого этапа. Изменения поведения не смешивать незаметно со структурным переносом.

## Общие критерии завершения

- Проект разворачивается с нуля по инструкции.
- Все проверки CI проходят.
- Работает полный сценарий: регистрация, вход, создание игры, вопросы, проведение и результаты.
- Нет открытых паролей в БД и ответах.
- Нельзя изменять чужие ресурсы и управлять чужой игрой.
- Неуспешная замена ответов не уничтожает прежние данные.
- Некорректное WebSocket-сообщение не приводит к необработанной ошибке.
- Поведение при отключениях и перезапуске определено и проверено.
- Каждый модуль описан в `backend/docs/`.
